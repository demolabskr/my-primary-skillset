# 검증 스킬 만들기

제대로 된 프로젝트에는 실제 앱을 띄우고 사용자처럼 조작해서 동작을 증명하는, 스크립트로 정해 둔 방법이 있어야 한다. 앱을 실행하고, 기능 하나를 사용자 경로로 조작하고, 증거를 남기는 방법이다. 이 스킬은 그 방법을 저장소에 맞춘 프로젝트 전용 스킬 `verify-<app>`으로 만든다.

만드는 스킬의 독자는 사람이 아니라 다음 에이전트다. 그 에이전트는 이 앱을 처음 보고, 작업 도중에 이 스킬만 읽고 따라 한다. 설명 없이 읽어도 그대로 실행할 수 있게 쓴다.

시작하기 전에 [references/drivers.md](references/drivers.md)를 읽는다. 이 기기에서 쓰는 조작 도구, agent-browser 규칙, 정리 스크립트가 거기 있다.

## 1. 사용자가 아니라 저장소에 묻는다

아래 질문은 코드에서 답을 찾는다. 코드로 확인할 수 없는 것만 사용자에게 묻는다.

- **표면:** 사용자가 실제로 만지는 것은 무엇인가? 웹 화면, CLI나 TUI, 데스크톱 앱, API, 모바일 앱, 라이브러리 가운데 무엇인가? 표면이 여럿이면 주 표면 하나를 고르고 나머지는 적어 둔다.
- **실행:** 앱을 로컬에서 어떻게 띄우는가? 저장소가 문서로 정해 둔 개발 명령(package scripts, Makefile, README, `manage.py`)을 먼저 쓴다. 포트, 환경 변수, 시드 데이터, 인증을 적는다.
- **조작:** 에이전트가 앱을 프로그램으로 조작할 방법은 무엇인가? 저장소에 있는 하네스를 먼저 찾는다. Playwright 설정과 스펙, expectrl이나 PTY 도우미, curl로 부를 수 있는 엔드포인트, 디버그 포트가 그 예다. 없을 때만 drivers.md의 기본 도구를 고른다.
- **관찰:** 어떤 증거를 남길 수 있는가? 스크린샷, 접근성 스냅숏, 영상, 터미널 기록, 응답 본문, 로그, 종료 코드, DB 상태가 있다.
- **분리:** 인스턴스 두 개를 나란히 띄울 수 있는가? 포트, 데이터 폴더, 브라우저 세션을 나눌 수 있는지 본다. 나눌 수 없으면 만드는 스킬에 그렇게 쓴다. 공유 인스턴스를 두 곳에서 조작해 사용자 세션을 망가뜨리는 것보다 조작을 거부하는 편이 낫다.
- **기존 지침:** 프로젝트 `AGENTS.md`에 이미 브라우저 검증 규칙이 있는지 본다(예: "Webwright로 검증한다"). 있으면 새 스킬과 충돌하는 지점을 사용자에게 알린다. 사용자가 승인하기 전에는 그 규칙을 고치지 않는다.

체크아웃이 그대로는 빌드되지 않거나 실행되지 않으면, 먼저 고치거나 무엇이 막는지 정확히 보고한다. 깨진 상태를 기준으로 쓴 스킬은 틀린 절차를 가르친다. 검증과 상관없는 파일이 없어서 실행이 막히는 경우(API가 쓰지 않는 정적 폴더, 예시 설정 파일)에는 만드는 스킬이 그 파일을 만들어도 된다. 이때 검증용 임시 파일이라고 분명히 표시하고, 정리 단계에서 지운다.

## 2. 스킬을 만든다

### 위치

- 원본은 `.agents/skills/verify-<app>/`에 둔다. Codex와 Claude Code가 같은 스킬을 읽게 하기 위해서다.
- Claude Code용으로 저장소 루트에서 상대 경로 링크를 만든다.

  ```bash
  mkdir -p .claude/skills
  ln -s ../../.agents/skills/verify-<app> .claude/skills/verify-<app>
  ```

- 증거는 저장소 루트의 `.verify-evidence/<run-id>/`에 남기고, `.gitignore`에 `.verify-evidence/`를 추가한다. 다른 위치가 저장소 관례에 맞으면 그 위치를 쓰고 스킬에 적는다.

### 본문

`verify-<app>/SKILL.md`에는 YAML 앞머리를 둔다. `name: verify-<app>`과, 앱 이름·표면·언제 쓰는지를 밝힌 `description`이 필요하다. 앞머리가 없으면 스킬이 등록되지 않는다. 본문에는 아래 절을 이 순서로 둔다. 모든 절은 1단계에서 실제로 확인한 내용으로 채우고, 자리표시자를 남기지 않는다.

- **실행(Launch):** 검증용으로 앱을 띄우는 정확한 명령과, 준비가 끝났음을 아는 방법(로그 한 줄, 프롬프트, 응답하는 경로)을 쓴다. 빈 데이터 폴더에서 시작해 마이그레이션과 시드 데이터까지 마친 쓸 수 있는 상태에 도달해야 한다. 준비는 프로세스가 응답하는 것이 아니라 쓸 수 있는 상태를 뜻한다. DB 상태 점검은 초기화 스크립트가 아직 도는 중에도 통과할 수 있다. 종료 방법도 쓴다. 금방 끝나는 CLI나 TUI에는 계속 띄워 둘 서버가 없다. 이때 실행은 바이너리 빌드나 의존성 설치를 한 번 하는 것이고, 조작은 매번 분리된 tmux 세션이나 PTY에서 새로 시작한다.
- **점검(Doctor):** "이 인스턴스를 조작해도 되는가?"에 답하는 읽기 전용 점검 하나를 둔다. 프로세스가 떠 있는지, 빌드와 버전이 맞는지, 포트를 이 실행이 띄운 프로세스가 쓰는지, 인증이 유효한지를 본다. 웹이면 `agent-browser session list`에서 지난 실패가 남긴 이 앱의 `verify-<app>-*` 세션도 확인한다. 무엇이든 이상해 보이면 에이전트가 이 점검부터 돌린다.
- **조작(Drive):** 이 저장소의 실제 선택자와 명령으로 하네스 사용법을 쓴다. 예시가 아니라 실제 값이어야 한다. 좌표나 탭 순서보다 안정적인 손잡이를 쓴다. 웹이면 ARIA 역할과 접근 가능한 이름, 레이블, `data-testid`를 쓰고, CLI면 프롬프트 문자열과 경로를 쓴다. 실행마다 drivers.md의 실행 환경 파일(`env.sh`)을 만들고, 매 셸 호출 첫 줄에서 `source`한다. agent-browser는 drivers.md의 세션 규칙을 따른다.
- **증거(Evidence):** 증명에 무엇을 남기고 어디에 두는지 쓴다. 증명 기준도 함께 쓴다.
  - 내부 setter나 테스트 전용 엔드포인트가 아니라 실제 사용자 경로를 탄다.
  - 마지막 화면만이 아니라, 한 조작과 그 결과 상태를 함께 남긴다.
  - 화면에 보이는 것과 함께 부수 효과를 확인한다. 쓰인 파일, 추가된 행, 보낸 메시지가 그 예다.
  - 운영 코드에 이미 외부 시스템을 분리하는 경계가 있는 곳에서만 모의 객체를 쓴다.
  - 안전한 경로가 dry-run이나 테스트 모드라면, 그 모드가 실제로 무엇을 건너뛰는지 이름을 믿지 말고 관찰해서 확인한다(파일, 네트워크, git ref). 어떤 dry-run은 네트워크에 접속하거나 브라우저를 연다.
- **정리(Cleanup):** 이 실행이 띄운 인스턴스를 내리는 방법을 쓴다. 프로세스 이름으로 죽이지 않는다. 이 실행이 띄운 것만 끝낸다. agent-browser 세션은 drivers.md의 정리 스크립트로 닫는다. 정리는 인스턴스와 임시 상태를 지우고 증거는 남긴다. 증거는 스킬이 정한 위치에 정리 뒤에도 남아 있어야 한다.
- **도우미(Helpers):** 스킬이 함께 두는 스크립트는 실행 권한이 있어야 하고, 호출 방법이 본문에 있어야 한다. 읽는 사람이 거꾸로 분석해야 쓸 수 있는 스크립트는 도우미가 아니다. agent-browser를 쓰면 `scripts/ab-session-cleanup.sh`를 `verify-<app>/scripts/`로 복사해서 스킬이 혼자서도 돌게 하고, 본문에는 저장소 루트 기준 경로로 호출법을 쓴다: `.agents/skills/verify-<app>/scripts/ab-session-cleanup.sh "$S"`.

## 3. 피처 맵을 만든다

`verify-<app>/features/README.md`와, 사용자가 쓰는 기능마다 파일 하나씩을 만든다. 처음에는 라우트, 명령, 메뉴, 문서에서 찾은 주요 기능 3~5개로 시작한다. 형태는 [references/feature-map-example/](references/feature-map-example/)를 따른다. README는 목차이고, 기능마다 파일이 하나씩 있다.

각 기능 파일은 사용자 관점에서 네 가지에 답한다. 그 기능이 무엇인지, 어떻게 들어가는지, 하네스로 어떻게 조작하는지, 어떤 관찰 가능한 최종 상태가 동작을 증명하는지다. H2 네 개는 `세부 기능`, `들어가는 길 (사용자 관점)`, `<하네스>로 조작하기`, `함정`이다.

시드 데이터에 어떤 사용 흐름의 전제 조건이 없으면, 그 흐름은 실패를 보고하고 이유를 그 기능의 `함정`에 적는다. 통과시키려고 흐름을 약하게 만들지 않는다. 피처 맵은 저장소의 검증 기준이다. 맵이 여러 진입 경로를 적어 두었는데 편한 경로 하나만 조작했다면 증명은 끝나지 않은 것이다.

## 4. 넘기기 전에 만든 스킬을 증명한다

만든 스킬의 지시를 처음부터 끝까지 한 번 따른다. 실행하고, 점검하고, 맵에 있는 기능 하나를 조작하고, 증거를 남기고, 정리한다. 기능은 하나면 충분하다. 나머지는 이후 실행이 맵으로 다룬다.

정리가 끝난 뒤 증거가 정한 위치에 아직 있는지 확인한다. 증거까지 지우는 정리는 이 단계를 통과하지 못한다. `agent-browser session list`와 `~/.agent-browser/`에 이 실행의 세션이 남지 않았는지도 확인한다.

실패한 부분은 고친다. 실패한 시도마다 만든 스킬의 정리 절차를 돌려서, 깨진 시도가 프로세스와 포트를 남기지 않게 한다. 한 번도 실행하지 않은 스킬은 초안이지 결과물이 아니다.

실제 대상 대신 대체 환경에서 증명했다면(새 VM 대신 컨테이너, 원격 스택 대신 로컬 스택), 대체 환경에서는 했지만 실제 대상에서는 하지 않을 준비 단계를 모두 적는다. 그 단계는 실제 대상에서 실행해 볼 때까지 검증되지 않은 것으로 남는다.

## 5. 넘겨줄 때

사용자에게 다음을 알린다.

- 만든 파일과 링크, `.gitignore`에 추가한 줄
- 4단계에서 조작한 기능과 남은 증거의 위치
- 프로젝트 `AGENTS.md`에 넣을 한 줄 제안. 예: "화면·CLI 동작 검증은 `verify-<app>` 스킬을 따른다." 기존 검증 규칙과 충돌하면 그 내용도 함께 알린다.
- 맵을 앱 변화에 맞게 유지하려면 `/maintain-verification-skill`을 쓰면 된다. 점검 주기는 사용자가 물을 때만 제안한다.
