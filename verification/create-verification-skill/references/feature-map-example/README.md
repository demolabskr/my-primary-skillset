# Notes 검증 맵

이 폴더는 Notes 앱에서 사용자가 보는 동작을 검증하는 기준 문서다. 앱을 조작하기 전에 이 목차를 읽고, 맞는 기능 파일을 레시피로 쓴다.

> 이 예시의 Notes 앱과 `notes` CLI는 형태를 보여 주려고 지어낸 것이다. 실제 맵에는 저장소에서 확인한 값만 쓴다.

## 기본 전제 조건

- 임시 데이터 폴더로 Notes를 `http://127.0.0.1:4173`에 띄운다.
- `NOTES_DATA_DIR=/tmp/notes-verify-$RUN_ID`로 실행마다 데이터를 나눈다.
- 제목이 `분기 계획`과 `장보기 목록`인 노트를 시드로 넣는다.
- `notes` CLI가 `PATH`에 있어야 한다.
- 점검(Doctor)을 돌려 URL, 데이터 폴더, 빌드 리비전이 기대값과 같은지 확인한다.
- 이번 검증 실행이 띄우지 않은 인스턴스는 조작하지 않는다.

## 조작 규칙

- 레시피에 다른 전제 조건이 없으면 모두 기본 상태에서 시작한다.
- 실행을 시작할 때 실행 환경 파일(`env.sh`)을 만들고, 모든 셸 호출의 첫 줄에서 `source`한다. 그 안의 `S="verify-notes-$RUN_ID"`, `E`, `ab()`를 쓴다.
- 요소는 `create-verification-skill`의 `references/drivers.md` 손잡이 표대로 찾는다. 표에 맞는 방법이 없을 때만 CSS 선택자를 쓰고, DOM 위치는 쓰지 않는다.
- 명령은 적힌 그대로 쓴다. 따옴표 안의 이름과 옵션을 바꾸지 않는다.
- 데이터를 바꾼 뒤에는 시드 데이터를 되돌린다. 정리할 때 증거는 지우지 않는다.

## 증명과 건너뜀 보고

- 마지막 화면만이 아니라, 사용자 조작과 그 결과 상태를 함께 남긴다.
- 화면 증명에는 접근성 스냅숏과, 앱이 무엇인지 보이는 스크린샷이 함께 있어야 한다.
- CLI 증명에는 명령, stdout, stderr, 종료 코드가 있어야 한다.
- 데이터를 바꾼 조작의 증명에는 저장된 값을 다른 읽기 전용 경로로 한 번 더 본 결과가 있어야 한다.
- 모든 증거에 기능 ID와 사용한 진입 경로를 적는다.
- 들어갈 수 없는 경로는 시도한 명령과 채워지지 않은 전제 조건으로 보고한다.
- 건너뛴 진입 경로를 다른 경로로 검증했다고 보고하지 않는다.

## 기능 파일 형식

기능 파일은 H1 제목과, 사용자가 보는 동작을 설명하는 문단 하나로 시작한다. 그 뒤에 H2를 정확히 네 개, 이 순서로 둔다.

1. `세부 기능`: 짧은 ID와, 동작마다 한 줄 설명을 적는다.
2. `들어가는 길 (사용자 관점)`: 사용자가 들어가는 모든 경로를 적는다.
3. `<하네스>로 조작하기`: `전제 조건:`으로 시작하고, 사용자 조작마다 정확한 명령과 관찰할 결과를 짝지은 굵은 제목 목록을 쓴다.
4. `함정`: 검증 실행을 헛돌게 하거나 무효로 만드는 함정을 적는다.

맵에는 구현 세부를 쓰지 않는다. 사용자 경로, 안정적인 손잡이, 필요한 상태, 명령, 관찰 가능한 증명만 적는다.
