# 검증 스킬 유지하기

피처 맵은 앱이 바뀌는 순간부터 낡기 시작한다. 이 스킬은 `/create-verification-skill`이 만든 스킬, 또는 실행·조작 절과 피처 맵을 갖춘 프로젝트 검증 스킬을 앱에 다시 맞추는 점검 절차다.

엄밀함의 단위는 문장이 아니라 기능이다. 모든 기능 파일을 코드로 확인하고 모든 기능을 실제로 조작하되, 항목 하나하나를 끝까지 따져 보지는 않는다.

## 결과

셋 가운데 하나로 끝내고, 어느 것인지 밝힌다.

- **clean**: 모든 기능을 코드와 실제 조작으로 확인했고, 고칠 것이 없다. 브랜치도 커밋도 만들지 않는다.
- **changed**: 증명된 문서·하네스·맵 수정을 별도 브랜치의 커밋 하나로 묶는다. 저장소가 PR로 일하고 사용자가 원하면 PR을 연다.
- **blocked**: 확인을 끝내지 못했거나, 증명된 수정을 안전하게 반영할 수 없다. 무엇이 막았는지 정확히 쓴다.

## 수정 범위

검증 스킬 자기 폴더만 고친다. `SKILL.md`, `features/`, 스킬이 가진 하네스 스크립트가 여기에 들어간다.

점검 중에는 제품 코드를 고치지 않는다. 맵에 적힌 동작을 앱이 더는 하지 않으면, 그것은 문서가 낡은 것(맵을 고친다)이거나 제품이 퇴행한 것(보고하고, 문서로 덮지 않는다) 둘 중 하나다.

## 절차

0. **대상 찾기.** 점검할 검증 스킬을 찾는다. 실행·조작 절과 피처 맵이 있는 프로젝트 스킬이다. 보통 `.agents/skills/verify-*/`에 있고, `.claude/skills/verify-*`는 그 링크다. 후보가 여럿이면 어느 것인지 묻는다. 하나도 없으면 대상을 지어내지 말고 멈추고, `/create-verification-skill`을 안내한다.

1. **목차 정리.** 피처 맵 README를 읽고 같은 폴더의 파일 목록과 맞춰 본다. 빠진 항목, 남는 항목, 중복, 깨진 링크를 고친다. 가볍게 하고, 목록을 자동 생성하지 않는다.

2. **코드 읽기.** 기능 파일마다 읽기 전용 하위 에이전트 하나를 동시에 띄운다. 하위 에이전트에게는 코드를 끝까지 읽고 근거 위치를 대게 해야 하므로, 발췌만 읽는 탐색용 에이전트보다 일반 하위 에이전트에 읽기 전용 지시를 붙여 쓴다(Claude Code는 `general-purpose`). 어떤 하위 모델을 쓸지는 기능 규모를 보고 메인 에이전트가 정한다.
   - 각 하위 에이전트는 "사용자가 쓰는 이 기능은 코드에서 어떻게 동작하는가?"를 설명한다.
   - 문서가 낡았을 가능성이 있는 곳을 근거 위치와 함께 짚는다.
   - 실제 조작으로 확인할 레시피 하나를 짧게 돌려준다.
   - 하위 에이전트는 앱을 조작하지 않고 파일을 고치지 않는다. 지시문에 "파일을 고치지 말 것"을 쓰고, 끝난 뒤 `git status`로 확인한다.
   - 돌려받을 형식: 기능 요약 / 코드 진입점 / 낡은 부분 또는 없음 / 레시피 하나.

3. **맞춰 보기.** 모든 기능 파일에 돌아온 요약이 있는지 확인한다. 겹치는 레시피는 되도록 적은 앱 상태로 합친다. 근거가 있는 낡은 부분은 직접 확인하고, 문제없다는 주장은 다시 증명하지 않는다. 최근 변경에서 맵에 없는 사용자 표면이 생겼는지 훑어본다. 빠졌다고 말하려면 구체적인 코드 경로가 있어야 한다.

4. **실제 조작.** 코드가 깨끗해 보여도 반드시 한다. 조작은 모두 메인 에이전트가 한다. 실행 방식은 이 스킬이 아니라 검증 스킬의 실행 절이 정한다. 조작을 시작할 때 검증 스킬이 정한 실행 환경 파일(`env.sh`)을 만들고, 이후 모든 셸 호출의 첫 줄에서 `source`한다. 서버와 화면은 오래 띄운 인스턴스 하나를 차례로 조작하고, 금방 끝나는 CLI는 조작마다 분리된 세션을 새로 띄운다. 모든 기능을 적어도 한 번 조작한다.

   실패가 어떻게 나든 점검 내내 세 가지를 지킨다.

   1. 마지막으로 이상한 일이 생긴 뒤 점검하지 않은 인스턴스는 조작하지 않는다. 첫 조작 전에 점검(Doctor)을 돌린다. 세션이 단위라면 새 세션마다 돌리고, 조작이 실패하면 다시 돌린다. 점검이 보지 못하는 실패(프로세스는 멀쩡한데 화면이 멈춘 상태)라면 점검이 통과하길 바라지 말고 알려진 상태로 되돌리거나 다시 띄운다.
   2. 지금까지 남긴 증거는 어떤 정리 뒤에도 남는다. 정한 위치에서 직접 확인하고, 남아 있으리라 가정하지 않는다.
   3. 조작이 띄운 것은 쓸모가 끝나면 남기지 않는다. 세션이 멈췄든, 끝났든, 공유 중이든 실패한 시도의 잔여물을 정리한다. 공유 인스턴스라면 인스턴스가 아니라 잔여물만 정리한다. agent-browser 세션은 검증 스킬의 정리 스크립트(`.agents/skills/verify-<app>/scripts/ab-session-cleanup.sh "$S"`)로 닫고, `agent-browser session list`와 `~/.agent-browser/`에 이번 실행의 세션이 남지 않았는지 본다.

   스킬이 낡아서 점검(Doctor)이 실패했다면 그것도 낡은 부분이다. 수정 범위 안에서 고치고 한 번만 다시 시도한다. 고친 내용 때문에 무효가 된 것만 다시 띄운다. 그래도 안 되면 `blocked`로 끝낸다.

   들어갈 수 없는 기능은 구체적인 전제 조건(인증, 권한, OS, 외부 상태)과 시도한 경로가 있을 때만 `verified-unreachable`로 적는다. 맵에 그 전제 조건이 없다면 그것도 낡은 부분이다.

   5단계에서 고친 하네스는 반영하기 전에 다시 실제로 조작해 본다. 마지막 정리는 이 재증명까지 포함한 이번 실행의 마지막 조작 뒤에 한다. 그래야 실행이 띄운 것이 실행보다 오래 남지 않는다. 증거는 스킬이 정한 대로 남긴다.

5. **분류.**
   - 사용자 관점 설명이 틀렸거나 빠졌다: 문서가 낡은 것이다. 고친다.
   - 앱은 제대로 도는데 하네스가 조작하지 못한다: 하네스 빈틈이다. 고친다. 고친 하네스도 생성 때와 같은 도우미 규칙(실행 권한, 본문에 호출 방법)을 따른다. agent-browser 찾기 명령이 안 통하면 `create-verification-skill`의 `references/drivers.md` 손잡이 표를 본다.
   - 앱 동작이 실제로 망가졌다: 제품 결함이다. 사용자에게 보고하고, 이번 수정에는 넣지 않는다.

6. **반영하거나 멈추기.** `changed`면 바꾼 파일을 모두 다시 읽은 뒤, 증명된 수정을 별도 브랜치의 커밋 하나로 만든다. 브랜치를 만들기 전에 `git log <기본 브랜치>..HEAD`로 다른 작업 커밋이 섞이지 않았는지 확인한다. `clean`이나 `blocked`면 커밋하지 않고 결과와 확인 범위를 그대로 보고한다.

실행 기록(확인한 기능, 들어갈 수 없었던 전제 조건, 확인된 낡은 부분, 결과)은 임시 위치에 짧게 남기고 커밋하지 않는다.
